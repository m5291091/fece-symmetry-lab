## 2. 発端と結論

**問い**: `domain/` の対称度がなぜ高く出るのか。顔がもともと対称だから当たり前なのか、計算を工夫すれば解決するのか。

**結論**: 両方だが、**現行の 2D 指標は精度不足ではなく、部位によって応答の符号が逆に出る。**

| 部位に非対称を注入したときの応答 | 現行 2D | 3D |
|---|---|---|
| 輪郭 | +0.905 | +0.138 |
| 口 | +0.147 | +0.238 |
| **目** | **−0.008（無反応）** | +0.200 |
| **鼻** | **−0.472（逆向き）** | +0.057 |

鼻を非対称にすると現行指標は「より対称になった」と報告する。較正で直る種類の問題ではない。

原因は 2 つの構造。

- **正中線あてはめ** — 鼻周辺の変位が基準線を引きずり、他部位の残差を動かす（測っていない 27 点が測っている全部を動かす）
- **眼アンカーの循環参照** — 33/133/263/362 は §8.3 の正規化基準そのもの。目の非対称は正規化に吸収される

**3D object symmetry 解析（鏡映 → ペア名入替 → Procrustes 重ね合わせ → 残差 RMS）が、全部位で正の応答を保った唯一の方式。したがって 3D 化は選択肢ではなく必要条件。**

この表は `requirement.md §8.6.6` へ要件側の事実として移した（W2 で記録済み）。docs だけの知識ではなくなっている。

## 6. E1 の結論 — W5 が W3 より前へ出た

実測は `docs/symmetry-metric-measurements.md` §12（すべて pt = 表示パーセントポイント。1pt = 0.01 IOD で、IPD の仮定に依存しない）。

**判定した 3 点**

1. **`100 × (1 - d)` は 3D では使えない。ただし理由は「張り付く」ではない。**
   当初の仮説「整数 % では誰を測っても 98%」は**外れ**。take01 では 97 / 98 / 99 の 3 種類が出る。
   しかし take01 のテイク内の幅は 1.205pt で、**同じテイクの注入応答（0.149〜0.896pt）より大きい**。
   つまり整数の跳びは信号ではなく**ノイズが境界を跨いだもの**。張り付くのではなく、**間違った理由で動く。**
2. **静止していれば信号は取れる。** take02（yaw 標準偏差 0.33°）では幅 0.434pt に対し
   注入応答が輪郭 0.833 / 目 1.301 / 口 1.750pt。**2〜4 倍**。ただし**鼻は 0.085pt で埋もれる**（§5 のゲイン 0.057 が pt でも再現）。
3. **セッション間の再現性。** 「先週の自分と比べる」が初めて成立しうる。E1 の設問には無かった発見。
   **ただし E1 の 0.031pt は take01/02 だけの値で、下方修正済み**（下記 §6.2）。

**W5 の設計課題は「スケールの付け替え」ではなく「何と比べた値かを決めること」。** 使えると分かった軸は
(a) 同一人物・同一セッション内の相対変化、(b) 同一人物・セッション間。**人と人の絶対比較は未測定**で、
現行式では文献の信号全幅 2.11pt に対し表示が 2pt 幅へ押し込まれる。

## 6.2 E2 の結論 — `remap_depths` は正しい。ただし 0.031pt は下方修正

実測は §13。**判定: 窓幅と α に相関なし・β ≈ 0 → `remap_depths` は正しい。W3 の障害は消えた。**

決め手は**対照**。α 単体では「恒等を除く」窓幅相関が +0.5326 あるが、`z` を一切使わない

**下方修正: セッション間ばらつきは 0.031pt ではなく 0.30pt。**

## 7. 追跡ズーム経路 — 解決した部分と残った部分（Z1）

**`z` の写像（`remap_depths`）は E2 で検証済み。以下は経緯の記録。**

W1 で `remap_depths` を「窓の幅比を掛けるだけ」と定義したが、実測はすべて landmarker を直接叩いており `TrackingZoomLandmarker` を通していない。`ui/camera.py` はリアルタイム経路を常にこれで包むので、**この写像はリアルタイムの `z` すべてに掛かる。**

```
一定倍率で外れている       → d_3d が定数倍ずれるだけ。姿勢不変性は壊れない
窓の大きさに応じて外れる   → 被写体が動くたびに倍率誤差が変動する
                            ＝ 3D 化で消そうとしているノイズが戻る
```

`z` のスケール誤差は §8.5.1 の正規化（3D 両眼間距離）を通じて xy との比率を歪めるので、定数倍としてきれいに相殺されない。

**→ E2（§13）で解決。** 窓幅を 5 倍動かしても α の全幅は 0.025 で、`z` を使わない対照より小さい。β は誤差予算の 1/156。**この経路のリスクは消えた。**

**残ったのは Z1 — 追跡ズーム経路のフレーム欠落。** 直叩きが単一顔を返したフレームのうち take01 7.2% / take02 **29.7%** / take03 7.5% を zoom 経路が落とす（5Hz では 15 / 28 / 18%）。表示の値は変えないが更新頻度に効く。

統制実験では、同じ切り出し画像に対し**新品の検出器は 40/40 単一顔、直前に全フレーム検出を通した検出器は 11/40 で 2 顔以上**。MediaPipe VIDEO モードは**同じ大きさのフレームを流し続ける限り**状態を持たない（§1）が、追跡ズームは毎フレーム入力サイズを変える。

**ただし説明は完結していない。** 統制実験の失敗域（窓幅 0.50 / 0.65）と take02 が実際に動いている帯（0.334）が重ならない。また欠落 178 件のうち「2 顔以上」は 89 件で、残り 89 件の理由が未記録。**Z1 はまず機序の特定から。**

- **セッション間ばらつき 0.30pt の出所が未分離。** 「その日の顔の違い」なのか「撮り方の違い」なのか。撮り方なら揃えれば消せる。**E3 の主題**
- **検出器の抑制の内訳未分離**。「テンプレート抑制」と「区分アフィン変形という不自然な入力への応答低下」を切り分けられていない。0.26〜0.67 は真の抑制の**上限**として読む
- **対称化ワープの裏返りは無くなっていない**。W0 は「転送を止めた」だけで、発生数（1 フレーム中央値 7 個）は変わらない。非対称が大きい被写体ほど読み飛ばしが増える。根本対処（変位場の正則化またはメッシュ細分）は FR-034 の出力を変えるので別課題
- **座標平均の残存時間相関**（実測 ÷ 理論 = 6.18）の出所が未分離
- **再現性 ≠ 誤差**。記録したノイズ床はすべて再現性で、正解に対する誤差の下限にしかならない

- **作業単位ごとに必ずコミットしてから次のプロンプトを渡す。** W0 を未コミットのまま W1 を走らせ、`requirement.md` / `testbox.md` / `STRUCTURE.md` が両方のハンクを抱えて分離不能になった
- **`STRUCTURE.md` は untracked なファイルも数える。** `generate_structure.py --include-untracked` はディスク上の実体を見るので、追跡していない docs があるとファイル一覧 SHA-256 に混ざる。**docs を先にコミットしてから実装の作業単位へ入ること。** W2 では `docs/HANDOFF.md` が未追跡のまま `STRUCTURE.md` の hash に入った
- **zsh の対話シェルでは `#` がコメントにならない。** コマンド例に `# 説明` を書くと `pathspec '#'` エラーになる。`setopt interactive_comments` を先に実行するか、コメントを書かない
- **顔の映像・座標をリポジトリへ入れない**（不変条件 1）。`.gitignore` に `*.mov *.mp4 *.avi frames/ take*.json warped*.png` を追加済み
- **CLI の押し返しを歓迎する。** 2 回、監督側（このセッション）の診断が誤っていて CLI が実験で反証した。どちらも CLI が正しかった
  - `--mode` が効いていないと判断したが、MediaPipe Tasks 0.10.35 の FaceLandmarker は VIDEO モードでもフレーム間状態を持たない（「11 枚流した後の detector と新品で bit 一致」で反証された）
  - 対称化ワープは滑らかな場だから裏返らないだろうと予測したが、実測で 1 フレーム中央値 7 個裏返っていた
- 逆に、CLI の判断が正しくてこちらが承認したもの:
  - 鏡像テストで d の比較に index 入替が**不要**であること（ペア表そのものが鏡像写像 σ なので、幾何学的に正しい検出器なら厳密に一致する）
  - 部位別 `d_3d,p` を単一の重ね合わせから集計すること（部位ごとに解くと 6 自由度の消費でペア数の少ない部位ほど値が下がり、部位間の差が「非対称さ」ではなく「ペア数」を反映する）
- **「常に 0 を返す実装」への耐性は、実際に壊して確かめる。** W2 では 3 種の罠（2D 投影スケール / 部位ごと Procrustes / `AxisSplit` 常時 0）を仕込み、それぞれ 5 件・2 件・20 件のテストが落ちることを確認した。この確認方法を以降の作業単位でも使う
- **平均と中央値を混ぜない。** E1 プロンプトで §2 / §3 の**平均**を表示式へ通して机上値を作ったが、take01 の 2D は下裾が長く、実測の中央値と 0.92pt ずれた（3D は 0.12pt 以内）。分布の形を知らないうちに代表値を 1 つ選ばない
- **「N Hz へ間引く」は fps によって取りこぼす。** CLI が 5Hz 間引きを「0.2 秒以上空いた最初のフレーム」で実装したところ、take02（30.003fps）で 6 フレーム = 0.19998 秒となり実効 4.3Hz に落ちた。**目標時刻に最も近いフレームを選ぶ**形が正しい。CLI が自分で見つけて fps を固定した self-test を足した
- **監督側の仮説は「外れ方」まで報告させる。** E1 の仮説 2（整数 % で誰を測っても 98%）は外れたが、CLI が種類数を素直に出したので「張り付くのではなく間違った理由で動く」という**より悪い**実態が見えた。仮説に合う数字だけを求めない
- **n=2 の差を「再現性」と呼ばない。** §12.2 の 0.031pt を「セッション間再現性」として W5 の設計根拠にしかけたが、take03 を入れた途端 0.30pt になった。**2 点は再現性ではなく 1 本の線である**
