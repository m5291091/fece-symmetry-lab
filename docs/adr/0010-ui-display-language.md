# ADR-0010: UI 表示言語を日本語と英語から選べるようにする（FR-043）

- Status: Accepted
- Date: 2026-08-29
- Related requirements: FR-043, FR-031, FR-032, FR-042, §1.3.1 不変条件 1・2・4・8・11・12, §4.1, §4.3, §5.3, §5.3.1, §5.4, §10.2, §10.11, §10.12, §15.1, AC-I18N-01〜03, AC-AGEGATE-04, AC-BASELINE-04

## Context

`requirement.md` §3.2 の P1 は「日本語／英語 UI」を長らく掲げていたが、対応する FR も
受け入れ基準も持たなかった。利用者（プロダクトオーナー）は 2026-08-29 に、これを
実際の要件として具体化するよう指示した。

現状の `ui/*.py` は、画面へ出る日本語の文言をハードコードした文字列として持って
いる。`ui/hud.py` の `FULLSCREEN_BADGE`・`FULLSCREEN_HINT`、`ui/smoothing_panel.py`
の `SMOOTHING_HEADING`・`SMOOTHING_SCOPE_NOTE`・`HOLD_LABEL` のように、多くは
module-level の `Final[str]` 定数として宣言され、`tests/ui/` がそれを import して
文字列そのものを比較したり、`inspect.getsource()` でモジュールのソースを走査して
禁止語が含まれないことを確かめたりしている。この種の構造テストは `tests/ui/` の
8 ファイルにまたがって 50 本を超えて存在する（`test_camera.py` だけで 30 本以上）。

同時に、選択肢の文字列がそのまま `st.session_state` の値になっている箇所がある。
`ui/hud.py` の `HUD_POSITION_OPTIONS`（`"左上"` / `"右上"` / `"左下"` / `"右下"` /
`"非表示"`）は、選択肢であると同時に `HUD_POSITION_STATE_KEY` の session state 値
であり、CSS の配置を引く `HUD_PLACEMENTS` 辞書の鍵でもある。`ui/smoothing_panel.py`
も、`"0.4 秒"` のような表示用ラベル文字列をそのまま `SMOOTHING_STATE_KEY` の
session state 値として保存している。これらをそのまま多言語化すると、言語を切り
替えた瞬間に保存済みの値が新しい選択肢集合の中に存在しなくなる。一方で
`ui/camera.py` の `_BACKGROUND_MODE_LABELS`（`dict[BackgroundMode, str]`）は、値
そのものは `BackgroundMode` の列挙のままにし、表示だけを `format_func` で切り替え
ており、この問題を起こさない実装例として既に存在する。

3 つの判断が要る。**(a)** 翻訳をどんな鍵で引くか。**(b)** 訳が欠けたときにどう
振る舞うか。**(c)** widget の選択肢とその値をどう扱うか。加えて **(d)** 禁止語の
規律をどう両言語へ及ぼすか、**(e)** 翻訳資源をどこに置くか、の 2 点も併せて決める。

## Decision

### (a) 翻訳の鍵は日本語の原文そのものにする（gettext の msgid と同じ）

**記号鍵（`"hud.fullscreen.badge"` のような catalog key）にはしない。** 記号鍵化は
2 つの層を同時に書き換えることを強いる。1 つは production 側で、`ui/*.py` が持つ
`Final[str]` 定数を「日本語の原文」から「鍵」へ差し替える必要がある。もう 1 つは
テスト側で、`tests/ui/` がその定数を import して文字列比較や `getsource()` 走査を
している箇所すべてが、比較対象を鍵へ差し替えないと動かなくなる。

決定的なのは後者である。**日本語のリテラルを呼び出し側から追い出して別モジュール
の catalog へ移すと、`inspect.getsource()` でモジュールのソースを直接読んで禁止語
の不在を確かめている構造テスト群が、その瞬間から検査対象を読めなくなり、空振りで
通り続けるようになる。** テストは「落ちなくなった」だけで「守られている」ことには
ならない。原文を鍵にして呼び出し側のリテラルをそのまま残せば、この構造テスト群は
今までどおり同じ文字列を検査し続けられる。

### (b) 訳が無い鍵は日本語の原文へ落とす（fail-open）

英語表示中に空文字や鍵名がそのまま画面へ出るより、日本語の原文が残るほうが実害が
小さい。不変条件 11 が求める「欠測を静かに埋めない」は数値の話だが、文言について
同じ発想を適用するなら、原文を返すことは「埋める」ではなく「訳が無いという事実を
そのまま見せる」ことに当たる。訳し忘れを隠す経路にしないため、抜けは
`tests/ui/test_i18n.py`（新設）が翻訳表を静的に走査して機械的に検出する。実行時の
fail-open と、テスト時の網羅チェックを分けることで、両方の目的を両立させる。

### (c) widget の選択肢の値は翻訳しない。表示だけを `format_func` で切り替える

`HUD_POSITION_OPTIONS` と `HUD_POSITION_STATE_KEY` の組、`smoothing_panel.py` の
`_CHOICE_LABELS` と `SMOOTHING_STATE_KEY` の組は、いずれも**表示ラベルをそのまま
永続する値として扱っている**。この構造を保ったまま文言だけ英訳すると、言語切替の
たびに保存済みの選択が新しい options の集合から外れ、Streamlit はそれを見つからな
い値として扱って既定へ戻す。利用者から見れば、言語を変えただけで HUD の位置や
平滑化時間の設定が黙って消えたことになる。

これを避けるため、**選択肢の内部値は言語に依存しない識別子（英語の列挙値や既存の
日本語ラベルの原文）に固定し、画面に出す文字列だけを `format_func` で言語ごとに
切り替える。** `ui/camera.py` の `_BACKGROUND_MODE_LABELS` は `BackgroundMode` と
いう列挙を値に使い、ラベルだけを辞書引きしており、この方式の実装例として既に
存在する。新規の多言語対応もこれに揃える。

### (d) 禁止語の走査を翻訳表そのものに対しても回す

§5.3 と §10.11-2 の禁止語規律は、画面に何が出るかではなく、**その言語で何を言える
ようにするか**の規律である。訳語を用意した瞬間に規律を回避できるなら、規律は
言語の数だけ弱くなる。そこで、`tests/ui/test_i18n.py` は翻訳表の英語側の値に
対しても §5.3・AC-AGEGATE-04・AC-BASELINE-04 と同じ禁止語リストを直接走査する。
画面へ出る条件（どのページ・どの状態で表示されるか）を再現しなくても、翻訳表に
禁止語が入っていればその時点で落ちるようにし、走査対象を「実行結果」ではなく
「訳語の在庫」にする。

### (e) 翻訳資源は同梱の静的モジュールだけにする

不変条件 1・2 により、外部翻訳 API・オンライン辞書・Web フォント・CDN のいずれも
実行時に参照しない。英語表示のためだけに新しいフォントを読み込む必要も無い——
ラテン文字は既定の system font stack で問題なく描画できる。翻訳表は
リポジトリに同梱する 1 つの静的な Python モジュール（辞書）とし、`bootstrap_models.py`
のような取得ステップを新設しない。

## Consequences

- `ui/*.py` が持つ日本語の `Final[str]` 定数はそのまま残り、翻訳表の**鍵**として
  再利用される。これにより、リテラルを import して比較している既存の structural
  test 群（禁止語の不在検査を含む）は、変更なしで動作し続ける。
- `domain` / `application` / `adapters` の例外文言は、UI が `st.error` /
  `st.info` / `st.warning` へそのまま渡すもの以外は日本語のまま残る。これらの層は
  表示文言を持たない設計（CLAUDE.md §6）であり、翻訳の責務を追加で持ち込まない。
- f-string で動的に組み立てられる例外文言・警告文は、原文と完全一致しないため
  翻訳表の鍵として引けない。これらは英語表示でも日本語のまま残る既知の穴であり、
  AC-I18N-01 の「翻訳表に無い文言だけが日本語のまま残る」という許容範囲に収まる。
- widget の選択肢を `format_func` 方式へ揃えることは、`HUD_POSITION_OPTIONS` と
  `smoothing_panel.py` の選択状態の持ち方を書き換える実装コストを伴う。これは
  FR-043 の実装単位で行うべき変更であり、本 ADR は方針だけを固定する。
- 翻訳表の網羅性（訳の欠落）と禁止語の不在は、実行結果の描画テストではなく
  翻訳表そのものへの静的検査（`tests/ui/test_i18n.py`）で担保する。この検査を
  弱めたり削除したりすることは、禁止語規律を英語側でだけ緩めることと同義になる。

## Alternatives considered

- **記号鍵の catalog（`"hud.fullscreen.badge"` のような ID）を新設する。** 慣用的な
  i18n の形だが、(a) のとおり production とテストの両方で日本語リテラルを鍵へ
  置き換える全面書き換えを強いる。何より、`inspect.getsource()` で禁止語の不在を
  確かめている既存の構造テスト群がリテラルを見失い、検査が空振りで通るように
  なってしまう。採らない。
- **`gettext` / `.po` ファイルを導入する。** Python 標準の i18n 基盤だが、
  `.po`/`.mo` のビルドステップと外部ツールチェーンが増え、「同梱の静的リソースだけ
  を読む」という不変条件 1・2 の単純さに対して過剰である。翻訳表の在庫を静的検査
  する仕組み（(d)）も自作することになり、素の Python 辞書に対して行うのと手間が
  変わらない。採らない。
- **英語 UI を作らず、About ページにだけ英語の説明を置く。** §3.2 の P1 が求めて
  いるのは Analyze を含む実際の操作画面の多言語化であり、About だけの英訳では
  HUD・タブ名・位置誘導・レポートの言語が日本語のまま残る。要件を満たさないため
  採らない。
