# ADR-0005: 参考年齢の表示ゲート（age-gate/1.0.0）

- Status: Accepted
- Date: 2026-08-15
- Related requirements: FR-038, FR-022, §1.3.1 不変条件 7, §9.2, §10.8, §10.11, §16, §22.5, AC-AGEGATE-01〜04

## Context

FR-022 は「対象範囲外には推論を提供しない」と定めている。しかし採用モデル
`age-gender-recognition-retail-0013` は 18〜75 歳でしか学習されておらず、**範囲外だと
言う手段を持たない**。子どもの写真を入れても 20 代の数字を返す。要件は書かれているが、
それを守る仕組みが存在しなかった。

`age-gate/1.0.0` は、478 点ランドマークから作った 41 次元の幾何特徴だけを入力に
「18〜75 歳の範囲内か」だけを返す LightGBM の 2 値分類器である。年齢は推定しない。
UTKFace（非商用研究限定）の配布注釈を正解ラベルに学習した。

4 つの判断が要る。**(a)** 不変条件 7 をどこまで解除するか。**(b)** 動作点をどこに置くか。
**(c)** 上限側をゲートするか。**(d)** モデルをどう配布するか。

## Decision

### (a) 不変条件 7 を「新規 ML モデル」についてのみ、この 1 件に限って解除する

**顔埋め込みの禁止は解除しない。** 解除するのは「新規 ML モデルを追加しない」の側だけで、
範囲は「幾何特徴だけを入力に、参考年齢を表示してよいかを決める 2 値分類器」に限る。

解除を正当化するのは、このモデルが**表示を減らす方向にしか働かない**ことである。新しい
値を利用者へ見せず、既存の値を出す条件を狭めるだけで、通れば何も起きず、通らなければ
参考年齢が消える。人物について新しい主張を増やさない ML モデルは、不変条件 7 が
防ごうとしていたもの（顔から属性を読む機能の増殖）とは向きが逆である。

他のモデルを追加するときは §1.3.1 を改めて改訂すること。この ADR は前例にならない。

### (b) 動作点は閾値 0.20（spec_revision 3）とする

**「明らかに範囲外と言える顔だけを弾く」**を目標とし、範囲内を誤って弾く率が 2% を
下回る動作点のうち最も高い閾値を選んだ。固定テストセット（n=3,806）の実測:

| 閾値 | 成人が参考年齢を失う率 | 0-5 歳 | 6-11 歳 | 15-17 歳 | 76 歳以上 | accuracy |
|---:|---:|---:|---:|---:|---:|---:|
| **0.20（採用）** | **1.1%** | **89.5%** | 33.1% | 4.3% | 9.6% | **0.8836** |
| 0.30 | 2.5% | 92.7% | 43.9% | 9.7% | 16.4% | 0.8761 |
| 0.6782（旧 rev2） | 15.2% | 98.8% | 73.4% | 44.1% | 45.2% | 0.8284 |
| 0.8953（旧 rev1） | 49.8% | — | — | — | 77.4% | 0.5938 |

（ベースライン = 常に「範囲内」と答える accuracy は 0.7759）

**なぜこれ以上上げないか。** 6〜11 歳の予測確率は中央値 0.419・p90 0.843 で成人と重なる。
この帯を取りに行くと必ず成人を巻き込む。rev2 の 0.6782 は 0.20 に比べ、成人の損失を
**14.1 ポイント増やして** 0-5 歳の検出を **9.3 ポイントしか増やさない**。増分の大半は
6-11 歳（+40.3pt）と 15-17 歳（+39.8pt）で、後者は 18〜20 歳と原理的に分離できない帯
であり、そこでの「検出」は精度ではなく境界の押し込みでしかない。

副次的な効果として、**誤って弾く側の群間差が消えた**。rev2 では 0.126〜0.189（女性 0.184 /
男性 0.126）だったものが、rev3 では 0.005〜0.019（女性 0.013 / 男性 0.010）になる。
保守的な動作点は、弾く回数そのものが減るぶん、弾き方の偏りも小さくする。

### (c) 上限側（76 歳以上）はゲートしない

この閾値での 76 歳以上の検出率は 9.6% で、実質的に全員を「範囲内」と答える。旧 rev1 の
0.8953 まで上げれば 77.4% まで届くが、そのとき成人の半数が参考年齢を失う。幾何特徴だけ
では皮膚の質感を見られないためで、**設計上の限界であり動作点の選び方では解決しない**。

したがって **FR-022 の「対象範囲外には推論を提供しない」は、本ゲートによっても
下限側の乳幼児についてしか満たされない**。この不足を「ゲートがあるから満たした」と
読み替えないことを §10.11-3 に明記した。上限側を塞ぐには別の特徴（皮膚テクスチャ等）が
要り、それは新しいモデルの追加になるため、改めて不変条件 7 の判断からやり直すこと。

### (d) ONNX をリポジトリへ同梱し、`onnxruntime` を runtime へ追加する

**同梱する。** 既存モデルと違い取得元 URL を持たない自作資産で、`bootstrap_models.py` が
取りに行ける場所が無い。917KB と小さく、顔の画像・ランドマーク座標を含まない（41 個の
集約特徴に対する決定木の集合）。`.gitignore` の `models/*` に対し
`!models/age_gate_model.onnx` の例外を 1 行足し、`configs/model-manifest.json` へ
`source: "bundled"` で登録して SHA-256 を追跡する（不変条件 6、§22.5）。

**`onnxruntime` を追加する。** §10.8 はもともと ONNX Runtime を禁止しており、年齢・性別
モデルはそれを避けるために `cv2.dnn` で動かしている。しかしこのモデルは `ai.onnx.ml`
ドメインの `TreeEnsembleClassifier` であり、`cv2.dnn.readNetFromONNX` は `nodes_modes`
（`BRANCH_LEQ` / `LEAF`）を解釈できず読み込みに失敗する（実機で確認）。ニューラルネット用の
推論器では**原理的に実行できない**ため、代替がない。追加の理由はこの 1 件に限り、年齢・
性別モデルは onnxruntime へ移さない——移すと ADR-0003 が固定した変換 contract と parity
検証の前提が変わる。学習用ライブラリ（LightGBM を含む）は runtime lock へ入れない。

## Consequences

- **成人の 1.1% は参考年齢を見られなくなる。** 仕様上の代償として受け入れる。判定不能の
  ときも表示しない（安全側の既定）ので、実際の非表示率はこれをやや上回る。
- **このゲートは乳幼児ゲートであり、未成年ゲートではない。** 6-11 歳の 3 分の 2、
  12-17 歳のほぼ全員が通る。要件・UI・モデルカードのいずれにも「18〜75 歳の判定ができる」
  と書かない。**年齢認証・本人確認・未成年判定・入場制限へ使わない**（§10.11-1）。
- **ゲートの内部判断を利用者へ属性として提示しない。** 「18 歳未満と判定されました」
  「未成年です」は表示禁止で、「この画像では参考年齢を表示できません」までとする。
  下限側の発火と上限側の発火も区別して見せない（§10.11-2）。
- **0-5 歳の検出率には群差がある**（81.2%（Black, n=16）〜 92.2%（Indian, n=64)）。n の
  小さい群を含むが、隠さず model card と評価レポートへ載せる（§10.11-5）。
- **エクスポートには判定と版だけを記録し、生の確率を持たない**（§9.2）。確率は「その顔の
  幾何が乳幼児にどれだけ近いか」の連続値で、記録すると凍結閾値以外での再判定・順位付け・
  「どれだけ若く見えるか」という読み替えを可能にしてしまう。判定・版・凍結閾値の 3 つで
  当時の挙動は一意に辿れる。
- **contract fixture が再現性の要になる。** 特徴量の並びが 1 つでもずれるとモデルは黙って
  違う確率を返し、他のどのテストにも現れない。24 ケースの期待確率との一致（絶対誤差
  1e-5 以内）と、`feature_names` の 3 者一致（fixture / spec / domain 実装）を毎回検査する。
- **fixture は 0-5 歳のケースを含まない**（内訳は 18 歳 8 件・10 歳 8 件・76 歳以上 8 件）。
  contract test は確率の一致を見るものなので目的は果たすが、**ゲートが実効を持つ帯を
  fixture が覆っていない**。判定レベルの検証は domain の合成ケースで別に持つ。
- 動作点を変えるときは requirement・model card・評価レポートを同時に更新する。rev1 → rev2
  → rev3 はいずれも ONNX 同一のまま閾値だけを動かしており、`spec_revision` がその履歴を
  持つ（§22.5）。
