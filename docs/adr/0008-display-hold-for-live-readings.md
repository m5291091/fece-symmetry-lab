# ADR-0008: 表示の更新間隔（表示ラッチ）を利用者の設定として持つ（FR-041）

- Status: Accepted
- Date: 2026-08-16
- Related requirements: FR-041, FR-040, FR-013, §1.3.1 不変条件 11, §5.2, §5.4, §8.7, §11 NFR-003, §14.3e, §15.1, §15.2, AC-HOLD-01, AC-HOLD-02, AC-DISPLAY-04

## Context

FR-040（ADR-0007）で §8.7 の EMA 時定数 `tau` を利用者へ開いた。依頼の目的は
**「リアルタイムでは数値がすぐ変わってしまうのを防ぐ」**ことだった（2026-08-16）。

`tau` を伸ばすと、フレーム間の**変化量**は小さくなる。しかし画面上の数字が
**動く頻度**は下がらない。EMA は連続時間のフィルタなので、平滑値は新しいサンプル
が来るたび必ず動く。しかも HUD と詳細結果は §11 NFR-003 に従って 4〜5Hz で更新
される。結果として、`tau = 5 秒` にしても「98.42% → 98.41% → 98.42%」が毎秒 5 回
入れ替わる。表示は小数 2 桁（§5.2）なので、この桁は必ず揺れる。

つまり依頼は `tau` だけでは満たせない。満たすには、**画面へ出す値を差し替える
頻度そのもの**を落とす必要がある。

3 つの判断が要る。**(a)** 何を保持の単位にするか。**(b)** 保持してはいけない
のはどの瞬間か。**(c)** どの層に置くか。

## Decision

### (a) 保持するのは「1 フレーム分の解析結果」そのものにする

**個々の数値ではなく、`AnalysisOutcome` を丸ごと保持する。**

素朴な実装は、表示する数値ごとにラッチを持つことである（全体の対称度に 1 つ、
部位別に 4 つ、…）。これは採らない。数値ごとに更新のタイミングが独立すると、
**同じ画面の別々の場所が別々の瞬間の測定を出す**状態が生まれる。§8.6.3 の
「全体のスコア」の計算過程（H4）は、そこに並ぶ部位別の値が上の部位別表示と
**文字列として一致すること**を AC-DISPLAY-04 で要求している。数値ごとのラッチは
この一致を、保持時間の境界でだけ静かに壊す。

結果 1 つを単位にすれば、一致は構成から保証される。HUD の折れ線グラフ・参照平均
との差（FR-039）も同じ結果から作られるため、まとめて整合する。

### (b) 欠測への遷移と欠測からの復帰は、保持を打ち切って直ちに反映する

**これがこの機能で唯一の安全上の要点である。**

保持を素直に実装すると、「顔が外れた後も直前の数値が最大 5 秒間そのまま画面に
残る」という挙動になる。これは不変条件 11（欠測を古い値で埋めない）と NFR-013 に
正面から反する。品質ゲートが閉じているのに数値が出ている画面は、**測定が続いて
いるという嘘**である。

そこで、保持の判定には「値が届いているかどうかの型」を鍵として持たせる。品質
ゲートの状態、全体の対称度・全体のスコアの有無、部位ごとの有無——このいずれかが
変われば、保持時間の途中でも即座に publish する。逆側（欠測からの復帰）も同じ扱い
にする。復帰を遅らせると、顔を戻したのに数秒間 `—` のままという別の嘘になる。

言い換えると、**保持してよいのは「同じものが測れ続けている間の、値の細かい揺れ」
だけ**である。

### (c) ラッチは domain の純粋な部品にし、実体は pipeline が持つ

判定は「時刻・保持時間・鍵」だけで決まる純粋計算なので `domain/display_hold.py`
に置き、時計は注入する（§14.2 の domain 規約）。保持している値そのものは
セッション単位の状態なので、実体は `RealtimeLandmarkPipeline` が持つ。

UI 側は `pipeline.hold_for_display(snapshot)` を通した snapshot だけを読む。
HUD の fragment と詳細結果の fragment は独立に 5Hz で動くが、ラッチが 1 つなので
**どちらが先に呼んでも同じ結果を受け取る**。UI 側に 2 つ持たせると、同じ画面の
2 つの区画が別々の保持区間を刻むことになる。

**worker thread 側（`_analyse`）は一切通さない。** `SessionRecorder` への記帳・
エクスポート・`segment_id`・`config_fingerprint` はラッチの手前にあり、この設定
では何も変わらない。記録が間引かれないことは AC-HOLD-01 が固定する。

## Consequences

- 既定は 0 秒であり、そのときの挙動は従来と完全に同一である（ラッチは素通しする）。
  この機能を知らない利用者の画面は 1 ピクセルも変わらない。
- HUD の折れ線グラフは、保持中は同じ値を積み続けるため階段状になる。これは意図
  した見え方である——線が滑らかに動き続けるなら、数値も動いている。
- 保持中の値は「その瞬間に測れた値」であって「保持区間の平均」ではない。区間内の
  代表値を作る（平均する）ことは意図的にしていない。それは §8.7 の EMA が既に
  やっている仕事であり、2 か所で時間方向に均すと、画面の数値がどの時間窓のものか
  を誰も説明できなくなる。
- `tau` の上限を 30 秒まで伸ばした（FR-040）。ラッチが「頻度」を、`tau` が「量」を
  受け持つという分担がはっきりしたためである。95% 追従時間（= `tau × ln 20`）は
  UI に出ているので、30 秒を選んだときの代償（90 秒かけて追いつく）は画面から読める。

## Alternatives considered

- **表示の桁数を減らす（98.42% → 98.4%）。** 揺れは見えにくくなるが、`ui.readings`
  のフォーマッタは HUD・吹き出し・詳細・参照平均の差が共有しており、Image 側には
  対応する設定が無い。同じ測定値に 2 つ目の表示規則が生まれる危険が、得られる
  安定より大きい。採らない（将来やるなら、Image を含めた表示規則の変更として行う）。
- **`analysis_interval_ms` を遅くする。** 数値の更新頻度は確かに下がるが、これは
  解析そのものの間引きであり、EMA のサンプル数・エクスポートの記録密度・
  FR-030 の自動調整のすべてに影響する。表示の要求で測定を薄くしてはならない。採らない。
- **`st.fragment(run_every=...)` の周期を変える。** 一見簡単だが、この fragment は
  HUD の隠し要素を書き続ける役目も持つ（止めると HUD の数値が更新されなくなる）。
  また品質ゲートの状態遷移まで遅れて届くため、(b) の「欠測は即座に」が実現できない。採らない。
- **数値ごとにラッチを持つ。** (a) のとおり AC-DISPLAY-04 を境界でだけ壊す。採らない。
