# ADR-0007: 表示平滑化時間を利用者の設定として開く（FR-040）

- Status: Accepted
- Date: 2026-08-16
- Related requirements: FR-040, FR-012, FR-030, §1.3.1 不変条件 10, §5.2, §5.3, §5.4, §8.6, §8.7, §8.8, §15.1, §15.2, AC-SMOOTH-01, AC-SMOOTH-02, AC-AUTOTUNE-02

## Context

リアルタイム表示の数値は、§8.7 の時間ベース EMA を通した平滑値である。

```text
alpha_t = 1 - exp(-delta_t / tau)
ema_t   = alpha_t × raw_t + (1 - alpha_t) × ema_(t-1)
```

`tau` はこれまで `0.4 秒` に固定されていた。§15.2 は「Advanced 設定に手動編集 UI は
存在しない」と定め、`ema_tau_seconds` を品質ゲート閾値と同じ行——固定既定値、UI 非公開
——に並べていた。FR-030 と AC-AUTOTUNE-02 も、この値を「手動 UI・AI 調整のいずれの対象
にもしない」と明記していた。

利用者（プロダクトオーナー）は 2026-08-16 に、**この移動平均の間隔を利用者が調整できる
ようにする**ことを指示した。`CLAUDE.md` §3 の優先順位ではユーザー指示が `requirement.md`
より上位であり、変更は可能である。判断すべきは「開くかどうか」ではなく、**開いても
不変条件 10（採点に影響する自動調整を持たない）と §8.6（較正されていない自由パラメータを
持たない）に触れないと言い切れるのはなぜか**、そして**開いた結果として何が壊れうるか**である。

3 つの判断が要る。**(a)** この値を開いてよい根拠は何か。**(b)** 変更時に何をリセットするか。
**(c)** UI の形をどうするか。

## Decision

### (a) `tau` は指標の係数ではなく表示フィルタの時定数なので、開いてよい

**開く。** §15.2 の「手動編集 UI を持たない」という規則から外す唯一の例外とする。

根拠は、§8.6 と不変条件 10 が守ろうとしている対象との違いにある。これらが禁じているのは
**測定値そのものを動かす較正されていない係数**である。§8.6 が感度係数 `k_p` と部位重み
`w_p` を廃止したのは、それらが「どの値を出すか」を選べてしまい、同じ顔から違う数字を作れて
しまうためだった。

`tau` はその種類の量ではない。EMA は入力列に対する線形時不変フィルタであり、`tau` が決めるのは
**同じ入力列を時間方向にどれだけ均すか**だけである。次の 3 つはいずれも `tau` に依存しない。

- 生値 `d_3d` / `d_3d,p` / `s_3d`（§8.5.1、§8.6.5）
- エクスポートの生値列（`distance3d_*_raw`、§9.2）
- 表示スケール `display-scale/1.0.0`（§8.6.7）のアンカー 2 点

依存するのは `distance3d_overall_smooth` と部位別平滑値、および画面に出る「いまの値」だけで
あり、これらは定義上「直近 `tau` 秒あたりの平均」である。`tau` を変えることは
**同じ測定列を別の時間窓で読むこと**であって、測定値を作り替えることではない。この点で
§8.6.3 の対称度表示（`100% - ずれ%`、可逆な線形変換）を許した論法と同じである。

同時に、`tau` は **AI 自動調整の対象にはしない**（FR-030 は変更しない）。理由は不変条件 10 の
条文そのままで、「採点に影響する自動調整を持たない」という主張の検証しやすさは、
自動調整が触れる値の集合が小さいことに支えられている。`tau` は表示にしか効かないが、
`config_fingerprint` に入り `segment_id` を動かす値であり、自動調整に持たせると
「自動で区間が切り替わる」経路が新しくできる。利用者の明示操作だけがこの値を動かす。

### (b) EMA はリセットし、品質ゲートのヒステリシスはリセットしない

§8.8 は「指標に影響する設定の変更」で EMA をリセットすると定めている。`tau` の変更はこれに
含める。**リセットしない場合、区間の境界をまたいで古い時定数で作った状態が新しい区間の
最初の値へ混ざる**——`ema_(t-1)` は「前の `tau` で均された値」であり、新しい `tau` の定義
（直近 `tau` 秒の平均）を満たさない。エクスポートは区間ごとに `ema_tau_seconds` を記録する
ため、混ざった値は記録と食い違う。

一方、**品質ゲートのヒステリシス（`valid_frames_to_ok` の連続数）はリセットしない。**
`FrameAnalyzer.update()`（`apply_advanced_settings` 経路）は閾値と `tau` をまとめて差し替える
契約なのでゲートごと作り直すが、`tau` だけを変える経路は別に用意する。ゲートを作り直すと
`Status` が `HOLD` へ戻り、`valid_frames_to_ok` 分のフレームを待つ間、数値が `—` になる。
`tau` は採点条件を動かさないので、この中断には根拠が無い。利用者が値を選び直すたびに計測が
止まると、選び比べるという操作そのものが成立しない。

**同じ値が再び届いたときは何もしない（冪等）。** これは実装の都合ではなく仕様である。
設定 UI は 5 Hz で再実行される画面の一部であり、毎実行で「現在の選択値」が pipeline へ届く。
ここを冪等にしないと EMA が毎フレーム作り直され、平滑化が事実上無効になったまま
「平滑化している」と表示され続ける。**壊れ方が静かである**ことが、この判断を仕様へ書く理由である。

### (c) 離散の段で選ばせ、選択の意味を数値で開示する

**連続スライダーではなく離散の段（0.1 / 0.2 / 0.4 / 0.7 / 1.0 / 1.5 / 2.0 / 3.0 / 5.0 秒）とする。**
`tau` の効き方は対数的で、0.40 と 0.45 の差は画面上で判別できない。連続値は「細かく調整できる」
という誤った印象——測定の精度が上がるかのような——を与える。段にすれば、選択のたびに
見た目が実際に変わる。範囲の両端は §15.2 の `0.05〜5.0` の内側に収める。

選択と同じ場所に、**その値から一意に導かれる量だけ**を示す。

| 開示する量 | 式 | 意味 |
|---|---|---|
| 63% 追従時間 | `tau` | 表示が新しい水準へ 63% 近づくまでの時間 |
| 95% 追従時間 | `tau × ln 20` | ほぼ追いついたと言える時間 |
| 実効サンプル数 | `tau ÷ (analysis_interval_ms / 1000)` | いま何サンプル分を均しているかの目安 |

いずれも上の EMA の式から導かれるだけで、新しい定数を持たない。§8.6 の「調整可能な係数を
持たない」に反しないのはこのためである。**推奨値・既定への誘導・「この値が正しい」を示唆する
文言は置かない**（§5.3）。短くすると反応が速くぶれも大きく、長くすると落ち着くが追随が遅れる、
という交換関係だけを述べる。

現在値は映像上の HUD にもテキストで出す（§5.2、§5.4）。数値の隣に時間窓が書いていなければ、
利用者は「いま何秒の平均を見ているか」を確かめるために設定タブへ戻る必要があり、
全画面表示中はそもそも戻れない。

## Consequences

- §15.2 の「手動編集 UI は存在しない」は `ema_tau_seconds` 1 件の例外を持つ規則になった。
  次に同じ要望が来たときは、その値が (a) の論法——測定値そのものを動かすか、時間方向の
  読み方だけを変えるか——のどちら側かで判断する。品質ゲート閾値は前者であり、開かない。
- `segment_id` が利用者操作で増える経路が 1 つ増えた。HUD の折れ線グラフは `segment_id` を
  世代識別子に使っているため、平滑化時間を変えるとグラフが空になって積み直される。これは
  意図した挙動である（古い時定数で描いた線と新しい線が同じグラフに並ぶほうが誤読を生む）。
- エクスポートの `ema_tau_seconds` は区間ごとに違う値を取りうるようになった。§9.2 の
  スキーマは変わらない——この値は元から config fingerprint の一部であり、区間をまたいで
  一定であるとはどこにも書かれていない。
- 静止画（Image）は §8.7 のとおり stateless で EMA を持たないため、この設定は現れない。
  `application.still_image.analyze_still_image` は平滑値を明示的に欠測へ落とし続ける。

## Alternatives considered

- **窓長（サンプル数）で指定させる。** 「直近 N フレームの平均」は直感的だが、
  `analysis_interval_ms` が FR-030 の自動調整で動くため、同じ N が指す実時間が黙って変わる。
  §8.7 が固定 `alpha` ではなく時間ベース EMA を選んだ理由（フレームレート変動で時間特性が
  変わらないこと）をそのまま捨てることになる。採らない。実効サンプル数は**導出値として
  表示するだけ**にとどめる。
- **移動平均（単純平均）へ置き換える。** 利用者の言う「移動平均の間隔」に最も素直に対応するが、
  §8.7 の式・§9.2 の列・§8.8 のリセット条件・部位別 EMA（H1）のすべてを書き換えることになり、
  変更の規模が要望に対して大きすぎる。EMA の `tau` は「直近 `tau` 秒あたりを均す」という
  同じ役割を果たし、リングバッファも持たない。採らない。
- **`tau` を変えても EMA をリセットしない。** 表示は滑らかにつながるが、(b) のとおり
  区間の記録と食い違う。採らない。
