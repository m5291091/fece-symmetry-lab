# ADR-0009: 結果レポートを HTML で書き出し、顔写真を含む図を埋め込む（FR-042）

- Status: Accepted
- Date: 2026-08-16
- Related requirements: FR-042, FR-021, FR-017, FR-034, FR-035, §1.3.1 不変条件 1, §5.3, §9.1, §9.2, §9.6, §10.4, §10.7, §14.4, AC-SUMMARY-01〜02, AC-REPORT-01〜03

## Context

エクスポートは FR-017 として既に動いている。Camera と Image は**同じスキーマ・同じ出力経路**を
共有しており（`ui/export_panel.py`、違うのは文言と widget キーだけ）、出るのはレコードスキーマ
v4.0（§9.2、約 50 列）の CSV と JSON である。Camera は解析フレーム 1 枚 = 1 行で最大 3,000 行、
Image はちょうど 1 行になる。

利用者（プロダクトオーナー）は 2026-08-16 に「エクスポート機能を作成してほしい。リアルタイムと
画像アップロードで出力方法が変わる」と指示した。現状を調べたところ、**出力方法が変わるはずの
ところが変わっていない**ことが問題だと分かった。加えて 3 つの欠落がある。

1. **FR-021（セッション要約）が要件だけあって未実装。** 3 分のセッションは 1,400 行になり、人が
   読める結果ではない。ここがリアルタイム固有の話で、1 枚しかない Image には分布そのものが無い。
2. **人が読む形式が無い。** CSV / JSON はどちらも再現性のための機械可読な台帳である。
3. **図が一切出ない。** 対称化オーバーレイ（FR-034）・対称化画像（FR-035）・ランドマーク重畳は
   画面にしか存在しない。Image は「その 1 枚の結果」なので、数値より図のほうが情報量が多い。

3 番目は不変条件 1（暗黙のファイル保存の禁止）と §10.4（アプリは画像をファイルへ書き込まない）に
正面から当たる。判断すべきは「解除するかどうか」ではなく、**どこまで解除し、何を解除しないか**である。

4 つの判断が要る。**(a)** 不変条件 1 をどこまで解除するか。**(b)** 形式を何にするか。
**(c)** リアルタイムの要約単位をどう切るか。**(d)** 図の埋め込みを既定でどうするか。

## Decision

### (a) 解除するのは「利用者の明示ダウンロード操作による保存」だけ

**解除する。** ただし範囲は次の 1 行に限る。

| 従来の禁止 | 扱い |
|---|---|
| 外部送信 | **解除しない。** ローカル完結のまま |
| 暗黙のファイル保存（自動保存・キャッシュ・ログ・一時ファイル） | **解除しない。** 自動では 1 バイトも書かない |
| 利用者の明示ダウンロード操作による保存 | **ここだけ解除。** 顔写真を含む図をレポートへ埋め込める |

この線引きが成立する理由は、**同じ線が既に引かれている**ことにある。FR-017 のエクスポートは、
左右差・姿勢・参考年齢という**顔由来の派生データ**を明示操作でディスクへ出している（§9.1 は
これらを「明示操作時のみエクスポート」と分類済み）。つまり「明示操作なら出してよい」という
判断は既に済んでおり、今回新しく加わるのは**顔画像そのもの**という 1 段だけである。

技術的にも、アプリがファイルを作るわけではない。`st.download_button` は応答を返すだけで、
ディスクへ書くのはブラウザである。localhost を越える通信も増えない（CSV / JSON と同じ経路）。

**代わりに、失うものを明示する。** ダウンロードされた HTML は共有先を制御できない。これは
About とレポート本体の両方へ書く（§10.4）。§10.7 の禁止用途と同じ場所に置くのは、この 2 つが
同じ性質——「アプリの外側で起きることへの注意」——だからである。

### (b) 単一 HTML ファイルにし、CSV / JSON は変えずに併存させる

**HTML。** 理由は 2 つある。図を `data:` URI で埋められるので 1 ファイルで完結すること、
ブラウザの印刷で PDF 化できるので追加の依存を持たずに済むことである。

**CSV / JSON は 1 列も変えない。** 台帳と読み物は目的が違う。台帳側へ要約列を足すと、
「1 行 = 1 解析フレーム」という v4.0 の意味が崩れる（要約はフレームに属さない）。ボタンは
3 つになる。

外部リソースは参照しない。CSS は inline、図は `data:` URI とする。開いた先で通信が起きる
レポートは、ローカル完結という前提をファイル単体では守れていないことになる。

### (c) 要約は `segment_id` ごとと全体の 2 段にする

**2 段。** `segment_id` はセッションのリセット・入力切替・指標に影響する設定変更（平滑化時間の
変更を含む、FR-040）で更新される。**設定が違う区間の値を同じ中央値へ混ぜてはならない**——
異なる `ema_tau_seconds` で均した値の中央値は、どの設定の測定とも言えない数になる。

segment の行には、その区間の `ema_tau_seconds` / `display_hold_seconds` /
`analysis_interval_ms` / `config_fingerprint` を併記する。「設定が違えば比べられない」という
ことを、表そのものから読み取れるようにするためである。全体の段も併せて出すのは、
セッション全体の有効率のように、区間へ分けると意味が薄れる量があるためである。

**要約の中身は 4 つに限る**（FR-021）。有効率・中央値・変動幅・主な HOLD 理由。ここへ
「代表値」や「総合評価」を足さない——1 セッションの記述統計以上のものを主張しないためである。

### (d) 図の埋め込みは既定 ON にする

**既定 ON。** 人間の明示判断である（2026-08-16）。

このアプリの既定は一貫して安全側で、FR-038 の年齢ゲートは「判定不能なら表示しない」、
FR-041 の表示ラッチは「欠測なら保持を打ち切る」という形を取ってきた。その系列で言えば
既定 OFF が自然であり、レビュー時にもそう提案した。**採らなかったのは利用者の判断である。**

この判断の下で失われる安全は「ボタンを押すだけで顔写真がディスクへ出る」ことなので、
代わりに次の 2 つで補う。どちらも既定 ON と両立する。

- ダウンロード操作の**直前**に、顔写真を含むことを書く（押した後では遅い）
- レポート**本体**にも同じことを書く（ファイルを受け取った側にも届く）

OFF にしたときは図の節ごと消し、空の枠を残さない（`:empty` で畳む既存の作法と同じで、
空欄は「機能が動いていて失敗している」と読まれる）。

## Consequences

- 不変条件 1 は 3 つの禁止のうち 1 つだけが条件付きで解除された状態になった。次に同種の要望が
  来たときは、(a) の表のどの行に当たるかで判断する。外部送信と暗黙の保存は解除しない。
- Camera のレポートは、利用者が「この瞬間を対称化して見る」（FR-034）で明示的に取り込んだ
  フレームがあるときだけ図を持つ。**取り込んでいないライブ映像のフレームを勝手に埋めない**——
  それは明示操作による保存という解除範囲を外れる。
- FR-021 の要約は画面（詳細結果タブ）とレポートの両方に出る。純粋計算を domain へ置き、
  両方がそれを読む。片方だけが計算を持つと、同じセッションに 2 つの中央値が生まれる。
- 図は長辺 1,280px へ縮小してから符号化する。原寸（最大 12MP）を base64 で埋めると 1 ファイルが
  20MB を超え、共有も閲覧も現実的でなくなる。この縮小は表示専用で、測定値には一切用いない。
- §9.2 のレコードスキーマは変わらない。`report_version` は §9.6 が別に持つ。

## Alternatives considered

- **CSV / JSON へ要約列を足すだけにする。** 追加の形式を作らずに済むが、「1 行 = 1 解析フレーム」
  という v4.0 の意味が崩れる（要約はどのフレームにも属さない）。また人が読む問題は解決しない。採らない。
- **PDF を直接生成する。** 体裁は安定するが、`reportlab` / `weasyprint` 等の依存が増える。
  §13.3 の依存方針（推論 runtime を 2 つに限る等）と揃わないうえ、日本語フォントの同梱が要る。
  HTML＋ブラウザ印刷で同じ成果物が得られる。採らない。
- **Markdown にする。** 軽く差分も読めるが、図が別ファイルになり単体で完結しない。レポートは
  「1 ファイルを渡せば全部伝わる」ことに価値がある。採らない。
- **図を出さない。** 不変条件 1 に一切触れずに済むが、Image モードでは数値より図のほうが
  情報量が多く、要望の中心を外す。採らない。
- **全行の生データを HTML へ入れる。** 3,000 行は読めず、台帳としては CSV / JSON が既にある。
  レポートからは案内だけにする。採らない。
